## 1. Decisions needed from Sebastian

These change the design, so I need an answer before coding. My recommendation comes first in each.

**D1. Pipeline as a vendored library plus a standard assignment, with the agents still
justifying every setting.**
- The pipeline becomes a second vendored package, `eegpipe/`, next to `eegharness/`. It is
  committed into each project, protected by the guard and never edited by hand; a new kit
  version replaces it.
- In an "apply the pipeline" run the agents write only three things:
  - the project adapter (recording → epochs with metadata);
  - the settings file (`configs/pipeline.json`, every key with its source);
  - the plan.
- The library, its tests and the runner are not rewritten per study.
- What stays from v0.2/v0.3: the agents still decide and justify every paradigm-dependent
  value from `PARADIGM.md` (G5, G6, G17 i), and the methods-auditor still audits the plan,
  the adapter and the settings.
- What changes: the methods themselves are no longer built from scratch.

**D2. The SSVEP demo stays a from-scratch test on v0.3.1.**
- A v0.4 project vendors Sebastian's pipeline, so it cannot also be blocked from it. The
  demo's purpose (the agents must not see the existing pipelines) only holds on v0.3.1.
- Proposal: keep `04_experiments/ssvep-demo` on v0.3.1 with its blocklist, as instructed. It
  measures what the harness does without the pipeline.
- Later, and only if Sebastian wants it, build a second project, `ssvep-apply` on v0.4, on the
  same data with the "apply the pipeline" assignment. It measures what the pipeline adds.
- The demo's blocklist blocks `03_code` (the kit repository), and a v0.4 project gets its
  code by vendoring, so the two do not conflict.
- Pending from the last message: the v0.3.0 session in the demo folder still has to be closed
  before I can rebuild the demo from v0.3.1.

**D3. Port from the frozen commit now; tag v0.4.0 only after the P300 confirmatory run ends.**
- The code is ported from `cd5db15`, the commit the Stage-2 run uses, so the kit gets exactly
  the code being confirmed.
- I do not run the P300 tests while Stage 2 runs. They compete for CPU and GPU, and that
  runner's frozen retry rule makes a timed-out part terminal.
- The ported tests run in the kit.
- After Stage 2 ends:
  - I run the P300 suite once, in a scratch export (never in that folder), to produce the
    golden outputs the regression tests in §4 compare against;
  - any fix Stage 2 forces is ported before the tag.

**D4. Dependencies.**
- `eegpipe` core needs numpy, scipy and scikit-learn, at the versions [P] pins (scipy 1.18.1,
  scikit-learn 1.9.1). torch (2.13.0) is optional; it is used only by `networks`, `graph` and
  the SSVEP networks.
- `eegharness` stays numpy only.
- The kit test venv gets scipy, scikit-learn and a CPU build of torch. GPU tests are skipped
  without CUDA.

**D5. Generalizations [P] needs.** [P] is written for a binary P300 contrast and has these
binary assumptions:
- `fit_network` takes labels in {0, 1}, with class weights n / (2 n_c);
- priors [0.5, 0.5];
- the metrics CA_target and CA_nontarget;
- the F3(a) statistic is target − non-target;
- the null shuffles block targets within a file.

An SSVEP study has k ≥ 2 classes, so the port changes these (each keeps its P300 result as a
regression test):

| [P] binary assumption | Becomes |
|---|---|
| class weights n / (2 n_c) | n / (k n_c) |
| priors [0.5, 0.5] | uniform 1/k, or explicit priors |
| CA_target, CA_nontarget | per-class recall plus balanced accuracy |
| F3(a) target − non-target | a declared contrast (two conditions) |
| null shuffles block targets within a file | the null shuffles unit labels within declared strata |

Is that scope right, or should v0.4 stay binary and add k classes later?

**D6. Rules.** I propose:
- **G24:** `eegpipe/` is configured, never edited; any deviation from the library is a new
  module in the project, with tests, and a note in DECISIONS.md.
- **G25:** confirmatory runs only from a frozen commit with a clean tree. This is what the
  runner already enforces in [P]; G25 makes it a rule the auditor checks.

Both need your approval, per "Rules grow".

## 3. Paradigm settings (`configs/pipeline.json`, filled from `PARADIGM.md`)

Every key has a value and a `source`:
- a `PARADIGM.md` section;
- `header`, for measured values from the file header (G21);
- `profile:<name>`, a profile default;
- `plan`.

The validator refuses a key without a source. A `profile:` default must be confirmed or
changed in the plan, with a reason (G17 i), and the plan audit fails if one is left
unconfirmed.

**Profiles.** These are starting drafts and are never applied silently.
- `erp`: the P300 values above, scaled by fs.
- `ssvep`: the [M] values (§6), with stimulus frequencies, phases, harmonics and window
  length marked "from PARADIGM, required" (no default).

A setting that depends on fs is derived from fs and the profile's value in seconds or Hz,
never copied as a sample count: the epoch length, EEGNet `kernel_length` (fs/2 as in
Lawhern 2018), nfft and numtaps.

`PARADIGM.md` gets one new section, "Pipeline settings this study needs", written by the
paradigm-analyst. It lists the paradigm values (classes, unit, timing, frequencies, contrast)
with evidence, and the adapter and settings cite it.

## 6. SSVEP option (`eegpipe/ssvep/`, from [M])

Read at `f725369`, read-only. Paths are relative to `mas-ssvep-eeg-xai/`, and PF numbers refer
to `mas/05_PITFALLS.md`.

SSVEP studies have k ≥ 5 classes in [M], so this option depends on D5 (k classes).

Three changes apply to all four methods:
- **No hard-coded constants.** Stimulus frequencies, harmonics, sub-bands, fs, channels and
  window length become settings. Today they are module constants:
  - `TARGET_FREQS = [24, 20, 15, 10.9091, 8.5714]`
    (`src/features/ssvep/fbcca_extraction.py:28`);
  - `LEGACY_FS_HZ = 250` while the recordings are 256 Hz (PF-04);
  - positional channels `KEEP_CHANNELS = (1, 4, 5, 6)` (`src/features/ssvep/harmonic_psd.py:25`,
    PF-06).
- **Filter banks on continuous data.** They are applied to the continuous recording before
  cutting (G21, PF-14). The legacy per-window path is not ported:
  `fbcca_extraction.py:71`, `fbcsp_extraction.py:47`.
- **One protocol for everyone.** Every method runs under the same `folds` and `evaluate`
  protocol as F1–F4, so its scores enter the same paired comparison.
